# Архитектура мобильных приложений: Android и Kotlin Multiplatform

Версия 2.0 · 5 октября 2026 · Marwin  
Технологии сверены с релизами: 5 октября 2026 (см. раздел 15)

## 1. Назначение и область применения

Документ задаёт архитектуру мобильного приложения и правила, по которым проект проверяется на соответствие ей. Он используется в двух случаях: при проектировании нового проекта и при аудите существующего.

**Область.** Android-приложения на Kotlin и приложения на Kotlin Multiplatform (Android + iOS), включая вариант с нативным UI на iOS поверх общего кода.

**Вне области:**

- нативные iOS-приложения без общего Kotlin-кода, Flutter, React Native;
- выбор бэкенда, дизайн-система как продукт, аналитика, feature-флаги;
- безопасность (хранение секретов и токенов), подпись и обфускация релиза, crash-репортинг, доступность. Эти темы проверяются по отдельным стандартам.

### Как устроены правила

Каждое правило имеет код (`MOD-1`, `DATA-5`), уровень и способ проверки. В отчёте аудита на правило ссылаются по коду.

| Уровень | Значение |
| --- | --- |
| **О** — обязательно | Несоблюдение считается нарушением |
| **Р** — рекомендуется | Отступление допустимо, если оно зафиксировано как отклонение |

| Способ проверки | Что делает аудитор |
| --- | --- |
| Сборка | Убеждается, что правило проверяет сборка или CI: запрещённое изменение роняет сборку |
| Тест | Находит автоматический тест, который покрывает правило |
| Поиск | Ищет по коду запрещённые или обязательные конструкции |
| Ревью | Читает код и оценивает экспертно |
| Ручная проверка | Запускает приложение и воспроизводит сценарий |

### Отклонения

Отклонение — осознанное отступление от правила, записанное в репозитории проекта (ADR или `docs/deviations.md`) по шаблону из приложения B. Запись содержит код правила, суть отступления, причину и условие устранения.

- Зафиксированное отклонение от правила уровня **Р** нарушением не считается.
- Отступление от правила уровня **О** остаётся нарушением; запись показывает, что риск принят осознанно.
- Отступление без записи — нарушение при любом уровне.

### Результат аудита

По каждому правилу ставится одна из оценок: «соответствует», «отклонение зафиксировано», «нарушение», «неприменимо». Форма отчёта — в приложении A.

## 2. Параметры проекта

Параметры фиксируются до начала аудита: от них зависит, какие правила применимы и какие технологии считаются базовыми.

| Код | Параметр | Значения | На что влияет |
| --- | --- | --- | --- |
| P1 | Профиль | Android / KMP | Разделы 5, 15; правила `BLD-4`, `TECH-4`, `TST-8` |
| P2 | UI на iOS (только KMP) | Общий Compose Multiplatform / нативный SwiftUI | Правила `NAV-*` для iOS, выбор UI и навигации |
| P3 | Размер | Малый: до двух фич включительно. Иначе обычный | `MOD-8`, выбор DI |
| P4 | iOS в течение года (только Android) | Да / нет | `TECH-3` |
| P5 | Офлайн-изменения данных | Нужны / не нужны | `DATA-4`, выбор хранилища |

## 3. Принципы

Из семи принципов выводятся правила остальных разделов. Сами принципы напрямую не проверяются.

1. **Зависимости направлены внутрь.** `presentation → domain ← data`; domain не знает ни о UI-фреймворке, ни о хранилище, ни о DI.
2. **Фича — единица изоляции.** Фичи не импортируют друг друга и не делят таблицы; общее выносится в `core` или в контракт `api`.
3. **Источник правды — локальное хранилище.** Сеть наполняет кэш, UI читает из хранилища. Исключение — операции без локального состояния (поиск, платёж).
4. **UI-состояние выводится, а не присваивается.** Один поток состояния, собранный из источников комбинацией.
5. **Ошибки — часть сигнатуры и типизированы.** Репозиторий возвращает результат с `AppError`, а не бросает исключение.
6. **Всё, что влияет на результат, внедряется.** Время, диспатчеры и генерация id приходят через конструктор и подменяются в тестах.
7. **Правила проверяет машина.** Границы модулей, граф DI, стиль и тесты закреплены в CI.

## 4. Обзор

Слои зависят от domain и от core, а фичи не знают друг о друге: правка одной фичи не ломает другие, а domain тестируется без Android и iOS.

```text
                app / shared: граф DI и навигация верхнего уровня
                    │                                        │
                    ▼                                        ▼
  ┌──────────────── feature:x ─────────────────┐     ┌── feature:y ──┐
  │                                            │  ✕  │ те же три     │
  │  presentation ───▶  domain  ◀─── data      │     │ модуля:       │
  │  UI и держатель     чистый      хранилище, │     │ presentation, │
  │  состояния          Kotlin      сеть       │     │ domain, data  │
  └────────────────────────────────────────────┘     └───────────────┘
                    │                                        │
                    ▼                                        ▼
  core и design-system:  common · database · network · settings · design-system
```

Стрелка означает «зависит от». Фичи x и y друг друга не импортируют; связь между ними идёт только через модуль `api`.

## 5. Два профиля

Правила одинаковы для обоих профилей. Профили различаются тем, что общее, а что платформенное.

| Аспект | Android | KMP |
| --- | --- | --- |
| Модуль фичи | Android library или JVM-модуль | KMP-модуль: общий код и платформенные source set |
| Платформенный код | Напрямую Android API | Интерфейс в общем коде и реализация в платформенном source set (или `expect/actual`) |
| Domain и data | Любые JVM-библиотеки (с учётом `TECH-3`) | Только KMP-совместимые библиотеки |
| UI | Jetpack Compose | Общий Compose Multiplatform или нативный UI поверх общего presentation |
| Точки входа | `Application` и `Activity` | Приложение на каждой платформе и общий `shared`-модуль с инициализацией DI |
| CI | Linux | Linux и macOS для iOS-таргетов |
| Стоимость | Ниже: меньше конфигурации, шире выбор библиотек | Выше: сборка для iOS, уже круг библиотек |

**KMP оправдан, когда:**

1. iOS-приложение есть или запланировано в течение года, а бизнес-логика объёмная (синхронизация, офлайн, правила): дублировать её дороже, чем платить за KMP.
2. Команда пишет на Kotlin, а iOS-разработчики готовы потреблять общий модуль.
3. Предметная область совпадает между платформами почти без различий.

**Android достаточно, когда** iOS не планируется, логики мало или нужны библиотеки только для Android. Проект, разрезанный по этому документу, переводится в KMP последовательно: domain, затем data, затем UI.

## 6. Структура модулей

Базовая единица — фича из модулей `domain`, `data`, `presentation` и необязательного `api`. Общее живёт в `core`, граф DI собирается в точке входа.

```text
app/                  точка входа: инициализация, навигация верхнего уровня, сборка DI
                      (KMP: приложение на каждую платформу и общий shared-модуль)
core/
  common/             диспатчеры, AppError, AppResult, обёртка логгера
  database/           платформенный builder, конвертеры, помощники миграций
  network/            HTTP-клиент, сериализация, маппинг сетевых ошибок в AppError
  settings/           хранилище настроек пользователя
  testing/            fake-утилиты, тестовый диспатчер
design-system/        тема и общие UI-компоненты без бизнес-логики
feature/<name>/
  api/                (опционально) контракты для других фич
  domain/             модели, интерфейсы репозиториев, use case
  data/               реализации репозиториев, таблицы и DAO фичи, DTO, мапперы
  presentation/       UiState, держатель состояния, экраны, навигация фичи
  di/                 (опционально) регистрация зависимостей фичи
```

**Разрешённые зависимости:**

| Модуль | Может зависеть от | Не может зависеть от |
| --- | --- | --- |
| `feature:x:domain` | `core:common`, корутины, `api` других фич | UI-фреймворк, хранилище, сетевой клиент, DI-фреймворк, `data`, `presentation` |
| `feature:x:data` | свой `domain`, свой `api`, `core:*`, `api` других фич | свой `presentation`, `domain` и `data` других фич |
| `feature:x:presentation` | свой `domain`, `design-system`, `core:common` | свой `data`, хранилище, сетевой клиент, модули других фич |
| `feature:x:api` | `core:common` | любую реализацию, любой другой модуль фичи |
| `feature:x:di` | все модули своей фичи, `core:*` | модули других фич |
| `core:*` | другие `core:*` без циклов | любую фичу |
| `app` / `shared` | всё | — |

Контракт `api` реализует `data` той же фичи. Модуль `di` нужен там, где DI-фреймворк требует ручной регистрации: это единственное место, где встречаются все слои фичи без того, чтобы `presentation` видел `data`. Если фреймворк сам собирает регистрации из модулей, отдельный `di` не нужен.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| MOD-1 | `presentation` и `data` фичи зависят от её `domain` и не зависят друг от друга | О | Сборка |
| MOD-2 | `domain` не зависит от платформенных API, UI-фреймворка, хранилища, сетевого клиента и DI-фреймворка | О | Сборка |
| MOD-3 | Фича не зависит от модулей другой фичи, кроме её `api` | О | Сборка |
| MOD-4 | `api` содержит только интерфейсы и модели и зависит только от `core:common` | О | Сборка, ревью |
| MOD-5 | `core:*` и `design-system` не зависят от фич; между `core`-модулями нет циклов, `core:common` не зависит от других `core` | О | Сборка |
| MOD-6 | Граф DI и навигация верхнего уровня собираются только в точке входа | О | Поиск |
| MOD-7 | Правила MOD-1…MOD-5 проверяются автоматически: convention-плагином или архитектурным тестом в CI | О | Сборка |
| MOD-8 | Фича разрезана на модули. При P3 «малый» слои могут быть пакетами одного модуля с теми же правилами импорта, проверяемыми архитектурным тестом | Р | Ревью |
| MOD-9 | Модуль `di` фичи подключает только точка входа | О | Сборка |

Модуль без второго потребителя ради одной папки — лишняя стоимость конфигурации сборки, поэтому `MOD-8` разрешает пакеты для малых проектов.

## 7. Domain-слой

Domain — чистый Kotlin: он собирается и тестируется без Android и iOS и одинаково работает на JVM и в общем коде KMP.

**Что входит:**

- модели предметной области (`data class`, `enum`, `value class`);
- интерфейсы репозиториев;
- use case, которые добавляют логику над репозиторием.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| DOM-1 | Модели не содержат аннотаций хранилища и сериализации | О | Поиск |
| DOM-2 | Классы domain не содержат аннотаций DI. В профиле Android допустимы аннотации JSR-330 (`jakarta.inject`) как отклонение | Р | Поиск |
| DOM-3 | В интерфейсах репозиториев наблюдение — `Flow`, разовые операции — `suspend`; операции, которые могут завершиться ошибкой, возвращают `AppResult` | О | Ревью |
| DOM-4 | Use case существует, только если делает больше, чем проксирует вызов: комбинирует источники, применяет правила, сортирует или фильтрует. Иначе держатель состояния обращается к репозиторию напрямую | Р | Ревью |
| DOM-5 | Имя действия совпадает с поведением: `Complete…`, если обратного действия нет; `Toggle…`, только если действие переключает | Р | Ревью |
| DOM-6 | Время, диспатчеры и генерация id приходят через конструктор; прямых обращений к системным часам и `Dispatchers.*` нет | О | Поиск |
| DOM-7 | Статусы и типы — `enum` или `sealed`, не строки | О | Ревью |

Пример контракта репозитория и use case с логикой (имена условные):

```kotlin
interface TaskRepository {
    fun observeActive(sort: SortOrder): Flow<List<Task>>
    suspend fun refresh(): AppResult<Unit>
    suspend fun complete(id: TaskId): AppResult<Unit>
}

class ObserveActiveTasksUseCase(
    private val repository: TaskRepository,
    private val settings: TaskSettingsRepository,
) {
    @OptIn(ExperimentalCoroutinesApi::class)
    operator fun invoke(): Flow<List<Task>> =
        settings.observeSortOrder().flatMapLatest(repository::observeActive)
}
```

## 8. Data-слой

Data-слой реализует offline-first: UI читает из локального хранилища, а сеть его наполняет. Экран работает без сети, а ошибка запроса не теряет уже показанные данные.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| DATA-1 | `observe*` читает только из локального хранилища и отдаёт domain-модели | О | Ревью |
| DATA-2 | Единственная операция чтения, которая ходит в сеть, — `refresh()`. Исключение — операции без локального состояния (поиск, платёж) | О | Ревью |
| DATA-3 | `refresh()` заменяет кэш одной транзакцией, чтобы удалённые на сервере записи не оставались | О | Тест |
| DATA-4 | Для изменений данных в фиче выбрана и записана одна стратегия: «сначала сеть, затем хранилище» или «сначала хранилище и очередь синхронизации». В обоих случаях UI получает результат из хранилища. При P5 «нужны» применяется вторая | О | Ревью |
| DATA-5 | Публичные `suspend`-методы возвращают `AppResult`; `CancellationException` пробрасывается | О | Тест |
| DATA-6 | Операции «прочитать-изменить-записать» (переключение флага, счётчик) выполняются одним запросом, транзакцией или атомарным обновлением | О | Ревью |
| DATA-7 | Работа с хранилищем и сетью и маппинг списков выполняются на внедрённом диспатчере, не на main | О | Поиск, ревью |
| DATA-8 | DTO (сеть) и Entity (хранилище) — разные классы; мапперы лежат отдельно и покрыты тестами | О | Ревью |
| DATA-9 | Статусы в Entity — `enum` с конвертером типов, а не строки в запросах | Р | Ревью |
| DATA-10 | Реализации репозиториев, Entity, DAO и DTO объявлены `internal` | О | Поиск |
| DATA-11 | Первичное заполнение базы — отдельная операция с явным именем, а не условие внутри `refresh` | Р | Ревью |

```kotlin
internal class TaskRepositoryImpl(
    private val local: TaskLocalSource,
    private val remote: TaskRemoteSource,
    private val clock: Clock,
    private val dispatchers: DispatcherProvider,
) : TaskRepository {
    override fun observeActive(sort: SortOrder): Flow<List<Task>> =
        local.observeActive(sort).map { rows -> rows.map(TaskEntity::toDomain) }
            .flowOn(dispatchers.default)

    override suspend fun refresh(): AppResult<Unit> =
        appResultOf(dispatchers.io) {
            local.replaceAll(remote.fetchTasks().map { it.toEntity(clock.now()) })
        }
}
```

## 9. Presentation-слой

Экран — чистая функция от `UiState`, а состояние выводится из потоков в держателе состояния (ViewModel или эквивалент). Это убирает гонки, когда «загрузка» и «ошибка» перезаписываются из двух корутин.

```kotlin
data class TasksUiState(
    val tasks: List<Task> = emptyList(),
    val isInitialLoading: Boolean = true,   // данных ещё не было
    val isRefreshing: Boolean = false,      // идёт сетевой запрос
    val error: UiError? = null,             // тип, а не готовая строка
)
```

### Состояние и экраны

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| UI-1 | Один `UiState` (`data class`) на экран; данные не пропадают при ошибке обновления | О | Ревью, тест |
| UI-2 | Состояние выводится: `combine` источников и `stateIn`. Присвоений `_state.value = …` из `collect` нет | О | Поиск |
| UI-3 | Начальная загрузка снимается по первой эмиссии данных из хранилища или первому результату `refresh`, а не по пустому списку | О | Тест |
| UI-4 | Начальная загрузка и обновление различаются в состоянии, если на экране есть обновление по действию пользователя | Р | Ревью |
| UI-5 | Однократные события (навигация, уведомление) передаются через `Channel` или `SharedFlow`. Для простых ошибок допустимо поле `error` с `onErrorShown()` | Р | Ревью |
| UI-6 | Публичный API держателя — `uiState` и методы `onXxx`; изменяемые потоки объявлены `private` | О | Поиск |
| UI-7 | Конструктор держателя принимает только типы из domain | О | Сборка (`MOD-1`) |
| UI-8 | Экран разделён на `XxxRoute` (получает держатель, собирает состояние) и `XxxScreen(uiState, onXxx, modifier)` без состояния и без знания о DI | О | Ревью |
| UI-9 | У `XxxScreen` есть превью для каждого значимого состояния | Р | Ревью |
| UI-10 | Состояние собирается с учётом жизненного цикла: подписка снимается в фоне | О | Поиск |
| UI-11 | Держатель отдаёт типизированную `UiError`; текст подбирает экран из ресурсов. Текст исключений пользователю не показывается | О | Ревью |
| UI-12 | Строки интерфейса лежат в ресурсах, а не в коде | О | Поиск |

### Навигация

Фича отдаёт функцию регистрации своих экранов и типизированные маршруты. Переходы между фичами делает точка входа через колбэки, переданные в граф фичи. При нативном UI на iOS (P2) навигация iOS остаётся на стороне платформы, а правила ниже применяются к Android-части.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| NAV-1 | Маршруты типизированы (объекты или классы), а не строки | О | Поиск |
| NAV-2 | Фича не вызывает экраны другой фичи: переход описан колбэком, который связывает точка входа | О | Сборка (`MOD-3`), ревью |
| NAV-3 | Время жизни держателя состояния привязано к записи в back stack | О | Ревью |
| NAV-4 | Back stack и аргументы экранов переживают гибель процесса | Р | Ручная проверка |
| NAV-5 | Back stack вкладки сохраняется при переключении вкладок | Р | Ручная проверка |

## 10. Обработка ошибок

Единая модель — `AppResult<T>` в сигнатурах репозиториев и замкнутая иерархия `AppError`. Компилятор заставляет обработать ошибку, а UI различает её вид.

```kotlin
// core:common
sealed interface AppResult<out T> {
    data class Success<T>(val value: T) : AppResult<T>
    data class Failure(val error: AppError) : AppResult<Nothing>
}

sealed interface AppError {
    val cause: Throwable?

    data class Network(override val cause: Throwable? = null) : AppError
    data class NotFound(override val cause: Throwable? = null) : AppError
    data class Unknown(override val cause: Throwable? = null) : AppError
}

suspend fun <T> appResultOf(
    context: CoroutineContext = EmptyCoroutineContext,
    block: suspend () -> T,
): AppResult<T> = try {
    AppResult.Success(withContext(context) { block() })
} catch (e: CancellationException) {
    throw e
} catch (e: Throwable) {
    AppResult.Failure(e.toAppError())
}
```

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| ERR-1 | В проекте одна модель результата и ошибки, объявленная в `core:common`. `AppError` — данные (`sealed`), а не наследник `Throwable` | О | Ревью |
| ERR-2 | `CancellationException` никогда не превращается в результат | О | Тест |
| ERR-3 | Исключения типизируются в месте происхождения: `core:network` превращает сетевые исключения и HTTP-коды в `AppError`, выше маппинг не дублируется | О | Ревью |
| ERR-4 | `AppError` не содержит текста для пользователя | О | Ревью |
| ERR-5 | `Flow`-методы не возвращают `AppResult`: поток из хранилища не падает из-за сети | Р | Ревью |
| ERR-6 | Неожиданные исключения (`IllegalStateException` и подобные) попадают в `Unknown` и логируются | О | Ревью |

## 11. Внедрение зависимостей

Правила одинаковы для любого фреймворка. Domain от фреймворка не зависит (`MOD-2`), поэтому его замена затрагивает только регистрацию.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| DI-1 | Зависимости приходят через конструктор; service locator внутри классов не используется | О | Поиск |
| DI-2 | Синглтоны — только репозитории, база, сетевой клиент и хранилища; use case и держатели состояния синглтонами не являются | О | Ревью |
| DI-3 | Граф проверяется до запуска приложения: компилятором или тестом в CI | О | Сборка, тест |
| DI-4 | Декларации делаются по типу (конструкторные ссылки, автоподбор), а не позиционными `get()` | Р | Поиск |

**Как проверять граф (`DI-3`).** Компиляторный граф проверяет сборка. Для рантайм-графа нужен тест: он поднимает контейнер с модулем фичи и фейками инфраструктуры и разрешает публичные точки входа — репозиторий, контракт `api`, держатель состояния. В общем коде KMP проверки на JVM-рефлексии недоступны, поэтому тест пишется именно так.

| Критерий | Компиляторный граф | Рантайм-граф |
| --- | --- | --- |
| Где ловятся ошибки | При сборке | При запуске или в тесте графа |
| Нагрузка на сборку | Выше | Ниже |
| Порог входа | Выше | Ниже |
| Где подходит | Обычные и большие проекты | Малые проекты (P3) и прототипы |

## 12. Инфраструктура

Модули `core:*` не знают о фичах, а фичи не знают друг о друге. Чаще всего это нарушается в трёх местах: база данных, настройки и связь между фичами.

**База данных.** Реляционные библиотеки обычно требуют перечислить все сущности в одном объявлении, а `core` не должен знать о фичах. Поэтому класс базы объявляется в точке входа, Entity и DAO остаются в `data` своей фичи, а `core:database` даёт общие утилиты. Отдельная база на фичу оправдана, если фичи поставляются независимо или данные нужно удалять пофичево; цена — нет `JOIN` между фичами и несколько файлов.

**Связь между фичами.** Если фиче B нужны данные фичи A, есть два варианта:

1. `feature:a:api` отдаёт интерфейс с моделями domain-уровня, фича B зависит от этого `api`. Вариант по умолчанию.
2. У фичи B своя таблица, которую наполняет событие из фичи A (тоже через `api`). Подходит, если данные фичи B должны переживать удаление исходных данных фичи A; цена — дублирование.

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| INF-1 | Класс базы объявлен в точке входа или у каждой фичи своя база; `core:database` не содержит сущностей фич | О | Ревью |
| INF-2 | Схема базы экспортируется в репозиторий | О | Поиск |
| INF-3 | Каждое изменение схемы сопровождается миграцией с автоматическим тестом | О | Тест |
| INF-4 | Деструктивная миграция отключена в release-сборках | О | Поиск |
| INF-5 | Настройки пользователя (сортировка, флаги) лежат в хранилище настроек с потоками и атомарным обновлением. Бизнес-сущности вроде «избранного» хранятся в базе, чтобы список читался одним запросом | Р | Ревью |
| INF-6 | Сетевой клиент, сериализация и маппинг ошибок настроены один раз в `core:network` | О | Ревью |
| INF-7 | API фичи — интерфейс внутри её `data`; fake-реализации не попадают в release-сборку | О | Ревью |
| INF-8 | Фича получает данные другой фичи только через её `api` и не читает чужие DAO и таблицы | О | Сборка (`MOD-3`) |
| INF-9 | Фичи логируют через обёртку в `core:common`, а не через библиотеку напрямую | Р | Поиск |

## 13. Тестирование

Базовый инструмент — ручные fake: они работают одинаково в Android-тестах и в общем коде KMP. Mock-фреймворки, привязанные к JVM, в общем коде не работают, поэтому архитектура их не требует.

| Слой | Что проверяется | Чем |
| --- | --- | --- |
| domain | Логика use case | Тестовый ранер корутин, тестировщик потоков, fake репозитория |
| data | Мапперы, `refresh`, транзакция замены кэша | База в памяти, fake сетевого источника, фиксированные часы |
| presentation | Переходы `UiState` | Тестировщик потоков, подмена main-диспатчера, fake репозиториев |
| DI | Граф собирается | Компилятор или тест графа (`DI-3`) |
| Границы модулей | Нет запрещённых зависимостей | Convention-плагин или архитектурный тест (`MOD-7`) |
| UI | Ключевые экраны по состояниям | Превью; screenshot-тесты по желанию |

| Код | Правило | Уровень | Проверка |
| --- | --- | --- | --- |
| TST-1 | Каждый use case с логикой покрыт тестом | О | Тест |
| TST-2 | Для каждого репозитория проверены `refresh` (успех, ошибка сети, отмена) и замена кэша | О | Тест |
| TST-3 | Для каждого держателя состояния проверены начальная загрузка, обновление, ошибка и повтор | О | Тест |
| TST-4 | Асинхронные тесты идут через тестовый ранер корутин с виртуальным временем (`runTest`), а не `runBlocking` | О | Поиск |
| TST-5 | Тесты не зависят от реальной сети, системного времени и main-диспатчера | О | Ревью |
| TST-6 | Fake репозитория живёт в одном месте (`core:testing` или тестовые фикстуры фичи) и не копируется | Р | Поиск |
| TST-7 | Исправление бага начинается с теста, который его воспроизводит | Р | Ревью |
| TST-8 | В KMP общие тесты запускаются в CI. У общих модулей есть JVM-таргет, чтобы эти тесты шли и на Linux | Р | Сборка |

Первый тест нового проекта — проверка гонки состояния из `UI-3`: пустой список до завершения `refresh` не снимает начальную загрузку.

## 15. Технологии

Аудит проверяет свойство из колонки «Что проверяется», а библиотеки служат примерами того, чем оно достигается. Библиотека не из таблицы допустима, если свойство выполнено и выбор записан как отклонение (`TECH-1`).

| TECH-1 | Для каждой задачи выбрана технология из колонки своего профиля либо выбор зафиксирован как отклонение | Р | Ревью |
| TECH-2 | Технологии из колонки «Только унаследованный код» не используются в новом коде | О | Поиск |
| TECH-3 | При P4 «да» в domain и data используются только KMP-совместимые библиотеки | О | Ревью |

**Пояснения к выбору:**

- **DI.** Компиляторную проверку графа дают Hilt, Metro, kotlin-inject и Koin с Koin Compiler Plugin. Koin без плагина остаётся рантайм-графом и требует теста графа.
- **Навигация.** Decompose подходит, если навигация должна жить в общей логике, а не в UI.
- **UI в KMP.** SwiftUI — при высоких требованиях к нативному виду на iOS; Compose Multiplatform — ради скорости и единообразия.
- **БД.** SQLDelight — если важен подход «сначала SQL»; Room — если команда его знает. При P5 «нужны» берётся реляционное хранилище с явной политикой конфликтов, а не key-value.
- **Настройки.** multiplatform-settings — для простых значений без потоков.
- **Сеть.** Ktor в Android-проекте оправдан при P4 «да».
- **Сериализация.** Moshi и Gson допустимы в Android-коде, который не станет общим.
- **Тесты.** MockK допустим только в Android-тестах; Robolectric — если нужен Android-фреймворк без эмулятора.
- **Фоновая работа.** Задачи с точным временем и долгие задачи решаются платформенными механизмами отдельно.

## 16. Риски

1. **Стоимость нарезки.** Три–четыре модуля на фичу замедляют конфигурацию сборки; для малого проекта `MOD-8` разрешает пакеты.
2. **Изоляция данных при общей базе.** Класс базы в точке входа видит все сущности, поэтому изоляция держится на `internal` и проверке границ; без `MOD-7` она нарушается незаметно.
3. **Рантайм-DI.** Без теста графа ошибки обнаруживаются при запуске.
4. **Неоднородный слой use case.** По `DOM-4` держатель состояния обращается к репозиторию напрямую для простых операций: бойлерплейта меньше, но часть операций идёт через use case, а часть нет.
5. **Переход на `AppResult` в существующем проекте.** Затрагивает все сигнатуры репозиториев и тесты; наполовину его сделать нельзя.
6. **Переход Android → KMP.** Если в domain и data попали JVM-only библиотеки, перенос потребует их замены; `TECH-3` снимает риск заранее.
7. **Устаревание таблицы технологий.** Статусы библиотек меняются быстрее документа, поэтому дата сверки указана в заголовке, а таблица пересматривается не реже раза в полгода.
